the time checked — not that it is permanently true. Re-verify before

## Economic accounting (applies from Gate 1 onward, not just post-Gate-3)

Tracked via `src/lantern/revenue_ledger.py` (built and tested
2026-08-30, 9/9 passing), reading the same `reciprocity_chronicle.jsonl`
Chronicle the service already writes:

- `calls_received` — every `RECIPROCITY_COMPLETED`/`RECIPROCITY_FAILED`
  Chronicle event.
- `successful_paid_calls` — settled, either network.
- `failed_payments` — execution failed or event type is
  `RECIPROCITY_FAILED`.
- `verified_mainnet_settlements` / `gross_revenue_usd` — **only**
  entries with `settlement_status == "settled"` AND network equal to
  the configured mainnet id. This is the only number that ever counts
  as real revenue.
- `testnet_settlements` — settled, but on a non-mainnet network.
  Tracked for engineering visibility; explicitly excluded from
  `gross_revenue_usd`.
- `unverified_or_pending` — includes the service's own
  `"verified_pending_settlement"` intermediate status. Excluded from
  revenue by design (verified ≠ settled).
- `operating_costs_usd` — supplied by the operator/caller, never
  invented (e.g., CDP per-transaction fees above the 1,000/month free
  tier — $0.001 each per CDP's own published pricing).
- `net_contribution_usd` — always `gross - costs`, computed live as a
  property so it can never drift out of sync with the two inputs (a
  real bug in an earlier draft of this exact bug was caught by
  `test_settled_mainnet_payment_is_real_revenue` and fixed before
  merge).

No revenue has occurred. No transaction has settled on any network
(testnet or mainnet) through this service as of this writing — this
document draws that conclusion because no `reciprocity_chronicle.jsonl`
file exists yet in this environment (the service has never been run
here), not because of an assumption.
